**第五批：数据侧遗留**（承接上一批"未擅自发起"的那一项）

上一批把板块数据问题记为"未擅自发起"，因为当时判断"要重抓正文、耗时数小时、改变数据"。
追查之后发现**这个判断是错的**：板块名只存在 `meta.json` 的 `s` 字段里，
正文按期分片（`data/<刊>/issues/<年>-<期>.json`）完全不用动 ——
于是"重抓 85 MB 正文"这个前提不存在，只需**每期抓 1 个目录页**（求是 188 + 红旗 163 次请求）。

| 症状 | 真实根因（已逐条实网抓取验证） | 修法 |
| --- | --- | --- |
| 求是 137 期整期板块是"目录"（2587 篇） | **"目 录"是抓取脚本的兜底值，不是求是真实栏目**。旧版目录页用 `<font color="maroon">目 录</font>`，解析器只认 `<span style="color:#ba372a">`；且比较"目 录"只按半角空格，页面实际有半角/全角 U+3000/nbsp 三种写法 → 全被当成板块 | `is_section_heading()` 同时认 `maroon` 与 `ba372a`，并排除归一化后等于"目录"的标题 |
| 求是 2019–2020 年 7 期板块是"评论"（499 篇） | **"评论"是微博分享控件的产物**：老版本把文章页的 `<div class="fs-pinglun"><span class="big">评论</span>` 当成了栏目 | 同上，从目录页重新解析；来源站证实不了的板块名一律清空 |
| 红旗文稿 2022 篇板块是"目录" | 同一批兜底值 | 同上 |
| 2026 年 16~20 期整期无板块（95 篇） | 新目录页用 `标题│栏目` 标专栏，老脚本的 `current_section` **继承规则是对的**（`│` 只标在每栏第一篇，同栏后续文章继承），但漏了"目录"归一 | 刷新脚本按同一条继承规则解析，已全部刷回 |

同时修掉的三个**抓取脚本的老 bug**（从首次入库 `6640a65` 就存在，至今影响旧期）：

1. `href.startswith('http')` 过滤掉**协议相对 URL**（`//www.qstheory.cn/...`）→ 旧期目录页解析出 **0 篇**；
2. `f'/{year}' in href` 年份过滤 → 2026 年第 1 期（发布于 2025-12-31，URL 里没有 `/2026`）**整期 0 篇**；
3. "目 录"比较未归一化 → 被当成了板块。

**刷新结果**（`scripts/refresh_sections.py --apply`，只抓目录页、不动正文）：

| 刊物 | 处理 | 真实栏目 | 兜底板块名 | 结果 |
| --- | --- | --- | --- | --- |
| 求是 | 188 期 | 221 → **370**（+149） | "目录" 2587 → **0**、"评论" 499 → **0** | **0 条真实栏目被误清**（221 条逐一核对期次区间，全部保留） |
| 红旗文稿 | 163 期（164 期中 1 期目录页链接缺失） | 240 → **536**（+296） | "目录" 2022 → **0** | 13 篇因目录页未抓到，保留原值不动 |

**统一原则（本次新定）**：**只保留来源站目录页能证实的板块名**，其余一律清空，
前端归入"未分栏目"，且**不显示为板块名**（文章页/搜索结果/相关阅读里直接省略这一段，
免得让人以为求是真有个叫"未分栏目"的栏目）。
目录页抓不到就整期不动 —— 不用猜测去覆盖已有数据。

**同名栏目被改名，板块页会多出两张相似的卡片** —— 新增 `scripts/canonical_sections.py`
（归一表，每条都附来源站证据），合并 3 处：

- 求是 `体系化学理化研究`（2025 年第 19–20 期）→ `体系化学理化研究阐释`（第 21 期起改名）
- 党建研究 `学习贯彻习近平总书记关于党的建设的重要思想●征文` → `…·征文`（同一名字换了装饰符号）
- 党建研究 `专题策划·深入贯彻中央八项规定精神学习教育` → `深入贯彻中央八项规定精神学习教育`（来源站自己的前缀时有时无）

**刻意没合并**的：党建研究 `调查报告`（2020-12~2025-7）与 `调研报告`（2026-2~）——
虽然名字像，但来源站是两个不同标签，且 2020~2022 那批数据是旧版解析器抓的、
板块归属本身不够可靠，**没有证据就不合并**，保持来源站原样。

**必须说清楚的边界**：求是 **2019–2025 年 14 期（158 期、约 3000 篇）的栏目信息
在来源站已彻底下线** —— 实时目录页里 `│` = 0、红色标题 = 0，文章页也已无"栏目"字段

**体检**：`scripts/check_data.py` 新增两项断言 —— 兜底板块名（"目 录"/"评论"）必须为 0、
归一表里的旧写法必须为 0。当前实测：兜底值 **0 条**、未归一旧写法 **0 条**。

## 一、结论摘要

**站点当前的状态是"功能完整、排版扎实，但缺少现代阅读站点的三样东西：可控的排版、读完一篇之后的路、以及性能余量"。**

1. **排版参数几乎全部写死**——字号虽有 4 档可调，但**行距、页宽、段间距、首行缩进**都无法调节，而这几项恰恰是长文阅读舒适度的主要变量。当前 `line-height: 2.05` + 20px 字号在中文长文下偏松散，读者没有自救手段。
2. **读完一篇之后没有下一步**——没有上一篇/下一篇、没有同板块相关推荐、没有记住阅读位置。一篇 5000 字的文章读完，读者必须退回目录重新找。
3. **性能余量不足**——首页为了显示三行"3402 篇 · 188 期"就下载 **1.36 MB** 的 `meta.json`；正文搜索要下载 **4.9 MB ~ 18.5 MB** 的整年 JSON。在移动网络和办公网环境下这是最实际的痛点。

**推荐路线：保留 Chrome 69 兼容，用渐进增强做现代化。** 本文档 P0 / P1 全部条目均可在 Chrome 69 下正常工作，不与刚完成的兼容性修复冲突。

## 三、痛点清单与建议（按优先级）

### P0 — 直接决定阅读舒适度与首屏体验

#### P0-1　行距可调（舒适度第一痛点）

- **问题**：行高写死 2.05。20px 字号下是 41px 行高，在中文长文里偏松散，视线容易串行；但偏紧又会显得拥挤。不同读者、屏幕亮度、阅读姿势对行距的需求差异很大，写死等于替读者做了决定。
- **方案**：阅读设置面板增加"行距"三档（紧凑 1.75 / 标准 2.0 / 宽松 2.3），由 CSS 变量 `--article-lh` 驱动，值存 `localStorage`。
- **成本**：约 30 行 JS + 10 行 CSS。
- **Chrome 69**：✅ CSS 变量（Chrome 49+）与 `localStorage` 均无兼容问题。

#### P0-2　页宽可调

- **问题**：正文栏 760px（窄屏）/ 860px（宽屏）写死。860px 在 1600px 宽屏上只占 54%，左右留白偏大；平板竖屏上 760px 又显得拥挤。行长直接决定中文阅读的舒适区（一般 35~45 字/行）。
- **方案**：`--article-w` 变量，三档：窄 680px / 标准 760px / 宽 880px。
- **成本**：约 20 行。
- **Chrome 69**：✅

> P0-1 与 P0-2 建议合并成同一组"排版"设置，共用一套变量与持久化逻辑。

#### P0-3　首页不要为了计数下载 1.36 MB

- **问题**：`loadHomeCounts()` 循环 fetch 三刊 `meta.json`（595 + 391 + 377 KB），**唯一用途**是显示"3402 篇 · 188 期"。这是首屏最大的开销，与实际需要相差三个数量级。
- **方案**：抓取脚本额外产出 `data/counts.json`（三刊篇数/期数，约 1 KB），首页改读它；`meta.json` 推迟到用户进入杂志视图时再加载。
- **成本**：抓取脚本 +10 行，前端 +5 行。
- **收益**：首屏数据请求 1.36 MB → ~1 KB。
- **Chrome 69**：✅

#### P0-4　记住阅读位置

- **问题**：本刊文章普遍 3000~8000 字，中途被打断（电话、开会）后回来要重新滚一遍，属高频场景。
- **方案**：`localStorage` 存 `{url → 滚动比例}`；再次进入该文时，若已读 15% 以上则提示"继续上次阅读（63%）"，点击直接跳位。
- **成本**：约 40 行。
- **Chrome 69**：✅

#### P0-5　正文搜索按"期"分片加载

- **问题**：正文搜索需下载整年 JSON。党建研究 2026 年更是 **18.46 MB**——这个离群值有明确成因：早期抓取时把 **1120 条求是正文**（560 条 https + 560 条 http）混进了 `data/years/2026.json`，而这批内容属于另一本刊物，在党建研究下根本用不到。移动网络下点一次"仅正文"可能需要几十秒。
- **方案（两条路，建议先做 A）**：
  - **A（低成本，先做这个）**：清掉 `data/years/*.json` 里的跨刊污染（仅 `data/years/2026.json` 受影响，1120 条）。
    实测收益：`data/years/2026.json` **18.46 MB → 3.50 MB**，`data/years/` 整体 **29.69 MB → 14.73 MB（省 50%）**。
    ⚠️ 注意：**不要按 http/https 协议一刀切**——`2020.json` 的 17 条、`2021.json` 的 139 条、`2026.json` 的 222 条都是党建研究 2020/2021 早期文章的**合法正文**（官网当时只提供 http 地址），删掉会让这些文章变成"无全文"。**只删 `qstheory.cn` 域名下的条目**。
    然后再把 `years/<年>.json` 拆为 `issues/<年>-<期>.json`（党建研究 2026 有 10 期 → 单期约 350 KB）。
  - **B（体验最优）**：预构建正文倒排索引，只存"命中词 → 上下文片段"，搜索时先查索引（几十 KB），命中后再按需拉正文。
- **成本**：A 约半天（脚本 + 数据重建 + 一次全量重抓）；B 约 2~3 天。
- **Chrome 69**：✅

### P1 — 明显提升"读完之后"和"找得到"的能力

#### P1-1　上一篇 / 下一篇导航

- **问题**：读完一篇，没有任何线索指向下一篇。党刊是有强连续性的内容（同一议题跨期次），这个导航的价值比一般资讯站更高。
- **方案**：文章页底部按当前目录顺序给出上/下一篇（标题 + 板块 + 期号）；键盘 `←` / `→` 或 `J` / `K` 切换。
- **成本**：约 60 行。
- **Chrome 69**：✅

#### P1-2　补发布日期

- **问题**：文章头只有"2026年第二十期 ｜ 经济 ｜ 周维富 ｜ 约 5131 字"，**没有发布日期**。对党刊检索而言，日期是核心维度——读者常按"今年以来""全会前后"筛文章。数据源（求是网/共产党员网）页面本身带发布时间，抓取时丢掉是可惜的。
- **方案**：抓取时记录发布日期写进 `meta.json` 的新字段 `d`；文章头、搜索结果、目录列表都显示。
- **成本**：抓取脚本 + meta schema + 前端展示，约半天。
- **Chrome 69**：✅

#### P1-3　`/` 与 `Ctrl+K` 快捷聚焦搜索

- **问题**：搜索框只能点。桌面端读者每次检索都要先移动鼠标。
- **方案**：全局监听 `/`（输入框外时）与 `Ctrl/⌘+K` 聚焦搜索框，`Esc` 失焦并还原。搜索框内展示占位提示"按 / 快速搜索"。
- **成本**：约 20 行。
- **Chrome 69**：✅

#### P1-4　首行缩进开关

- **问题**：`text-indent: 2em` 是纸质公文习惯；屏幕阅读中"无缩进 + 段间距"的读者也不少（尤其大字模式下 2em 缩进很扎眼）。
- **方案**：设置面板加"首行缩进"开关，切换 `--article-indent`。
- **成本**：约 15 行。
- **Chrome 69**：✅

#### P1-5　相关阅读（同板块 / 同作者）

- **问题**：文章结束处是硬边界，读者失去继续阅读的抓手。
- **方案**：文章底部按当前板块列出同板块最近 5 篇（标题 + 期号），按用户实际浏览行为排序。
- **成本**：约 40 行。
- **Chrome 69**：✅

#### P1-6　目录与板块视图用真实封面

- **问题**：抓取脚本只下载**最新一期**封面（`assets/img/cover_<mag>.jpg`），所以首页好看，目录/板块视图是纯文字，视觉上明显偏素。现代杂志站点的封面/缩略图是最主要的视觉资产。
- **方案**：抓取脚本按期下载封面到 `assets/img/cover_<mag>/<year>-<issue>.jpg`；目录视图在期号手风琴展开时显示缩略图，板块视图在板块卡片上显示该期封面。
- **成本**：抓取脚本多一轮请求（每期 1 张，约 100 KB × 424 期 ≈ 40 MB，**建议只对近 3 年抓取**），前端中等改造。
- **Chrome 69**：✅ `<img loading="lazy">` 是 Chrome 76+，但**老浏览器会直接忽略该属性**（改为立即加载），不会报错，安全。

#### P1-7　正文搜索显示命中上下文

- **问题**：正文搜索结果只显示标题，读者无法判断命中内容是否是自己要的，必须点进去逐篇翻。
- **方案**：命中时展示正文中命中词前后各约 40 字的片段并高亮。
- **成本**：约 60 行，依赖 P0-5 的分片方案。
- **Chrome 69**：✅

## 四、关键决策：Chrome 69 的去留

现代化与 Chrome 69 兼容存在天然张力，需要明确取舍。

| | **保留 Chrome 69（推荐）** | 放弃 Chrome 69 |
| --- | --- | --- |
| 实现方式 | 现代特性一律渐进增强（`@supports` 兜底） | 直接用 `oklch` / `:has()` / `content-visibility` / `dvh` |
| 增量成本 | 每个现代特性多写一份兜底。本文档 P0/P1 **全部兼容**，不增加成本 | 现有兼容层（style.css 末尾 109 行 + 2 个子页兜底块）全部作废，需重写 |
| 主要风险 | 兜底块"写了但没生效"——**历史已发生过两次**（选择器漏前导点、gap 未归零） | Chrome 69 用户直接白屏 |
| 风险控制 | 已有 `scripts/check_compat.py` 兜住：任何 flex gap 容器没有对应兜底即报错 | — |
| 收益 | 覆盖办公机 / 内网机 / 老旧平板群体 | 视觉自由度更大，代码更简洁 |

**建议保留。** 站点 README 与 `docs/CHROME69_COMPAT.md` 已明确承诺支持 Chrome 69；而"读党刊"这个场景的用户结构里，办公机与内网机占比很高，这正是兼容性投入的实际回报。

**若将来决定放弃**，改动面是可控的：删除 `style.css` 末尾的兼容层 + 两个子页的兜底块 + `docs/CHROME69_COMPAT.md`，并把 `scripts/check_compat.py` 从"特性黑名单"改为"特性白名单"模式。建议先用 §5 的路线图跑 2~3 个月，看用户反馈再定。

## 六、不建议做的事

- **不要引入构建步骤或框架**——纯静态、零依赖是这个项目最有价值的属性（可直接用 `python -m http.server` 跑起来，仓库 clone 即用）。一旦上构建，README 里"clone 就能看"的承诺就没了。
- **不要为了"现代感"换成纯黑底 + 高饱和强调色**——党刊是长文连续阅读场景，深色高饱和非常刺眼。当前暖褐 + 暗红的主题是合适的。
- **不要加自动播放的装饰动效**——阅读页的注意力应该全部留给正文。
- **不要用 `oklch()` 等新色彩空间重写配色**——除非同步放弃 Chrome 69（见 §4）。
